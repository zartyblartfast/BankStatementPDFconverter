# Rule maintenance

## User workflow

- Exceptions keeps **Transactions needing categorisation** and its **Open transaction exceptions** count separate from **Optional rule review** and its derived group count. Missing future rules, disabled saved rules and different historical assignments are not open transaction exceptions. A different saved category can be intentional. Candidates are derived read-only from actual description normalization, not a new error queue.
- Corrections default to this transaction only. Checking **Also use this category for future matches** saves the transaction first, then opens a separate future-rule preview. The preview shows the exact matching key, current/proposed destination and enabled state, and every historical exact match. It never recategorises historical rows.
- Cancelling that preview leaves the saved category intact and the rule unchanged. A failed/unknown rule save is reported separately from the saved category. Report-refresh warnings remain visible. The search page reloads its existing URL, preserving filters/page.
- **Saved rules** is the main compact five-column table: merchant, rule category, rule subcategory, enabled status and two actions: **View details** and **Edit rule**. Disabled rules remain saved rules; differing historical categories appear as informational notices, not transaction errors. Missing rules never produce blank category/subcategory cells in this table. There are no per-row category selectors or extra action buttons. View details contains matching transactions and **Previous rule edits**, explained as a log that does not change past transactions. Edit/Add rule opens a labelled dialog; **Save changes** prepares a separate confirmation with **Confirm change** and **Cancel**. No write happens before confirmation. Cancelling confirmation leaves the form open with its unsaved fields and an explicit not-saved message; cancelling/Escape in the form discards edits and returns focus to its opener. Fields stack on narrow screens.
- **Suggested rules (count)** is a separate, initially closed section, opened automatically for matching searches/direct review links. It shows every distinct **saved transaction category / subcategory (transaction count)** for each missing-rule key in the displayed account scope. Category/subcategory pairs remain together even when narrow text wraps. These are historical saved assignments, not future-rule destinations. Where all suggested transactions have saved categories, the help reads: “Optional: these transactions are already categorised; add a rule only if future matches should use the same category.” Mixed or uncategorised views instead explain the distinction without claiming they are already categorised. Actual missing assignments are labelled **Uncategorised**; those groups link to **Categorise transactions first**, not Add rule. **Add rule** proposes an editable category/subcategory only when the full matching history across all accounts consistently supports one valid destination. Mixed, uncategorised or obsolete assignments require an explicit choice; an account viewing filter cannot hide conflicting evidence in a globally shared rule. Opening, filtering, sorting and cancelling never create a rule, learn a category or change transactions.
- Same destination and enabled state is a no-op. Selected/bulk category edits never write future rules.
- Legacy combined `remember_rule=true` requests to correction endpoints now fail **before** transaction/config writes, with instructions to use the separate preview. Existing search/report four-field category requests remain supported. The supported legacy Income vs Expenditure dialog now saves this transaction only, with a separate **Review future rules separately** link to Rules; it has no Remember checkbox or merchant-wide save. Known already-stored legacy HTML receives the same controls and save-function adaptation in memory, never a disk rewrite. A report-refresh failure after a committed legacy category save returns success with a saved-category warning and leaves that warning visible rather than reloading it away.

## Account review and sorting

Rules remain shared across all accounts; account identity is not a matching condition and is not written to the rule CSV. The **Review account** selector and find field form a read-only GET view (press Find to apply). Names and available IDs come from the accounts service/registry, including registered accounts without transactions; no UK/IoM names are hardcoded, no migration/setup runs. With no registry only All accounts is available; historical IDs are labelled as not registered rather than given inferred names.

- **All accounts** is the default (absent or empty `account_id`). It includes every stored rule, explicitly marks **No historical matches**, and lists derived missing-rule keys only in Suggested rules.
- **An individual registered account** shows keys with at least one exact historical match in that account, including agreeing assignments. Rules with no matches there are hidden, not disabled or deleted; an empty account has an empty list. Match/candidate counts refer to the displayed scope. History is always shared and unfiltered.
- **View details** uses that account view, adds an Account column with the actual name, and performs no writes. Unknown or repeated account selectors return HTTP 400 for both the page and inspect API instead of silently broadening the view.
- Click heading buttons for Rules **Merchant / exact matching key, Category, Subcategory, Enabled status** or read-only matches **Date, Description, Category, Subcategory, Account**. First click is ascending ↑; the next is descending ↓. Only the active heading gets the arrow/`aria-sort` direction. Native buttons support keyboard Enter/Space. Case-insensitive text ties retain original row order in either direction; ISO dates sort chronologically. Enabled status sorts by its displayed label (Disabled / Enabled). Suggested rules have independent Merchant and combined Saved category / subcategory heading sorts; saved-category sort metadata never masquerades as an existing future rule in the Add dialog. Sorting moves existing nodes, keeping unsaved dialog selections, search/account filters and exact transaction IDs intact; it neither fetches nor writes. A newly opened evidence view resets its sort.
- **Destination/disable/re-enable/undo confirmation is never account-filtered.** Both the preview and held stale evidence cover all matching historical transactions across all accounts, with account labels. A changed matching transaction in another account invalidates confirmation. The approval explicitly says edits affect future matches across all accounts, regardless of the review filter. Historical categories remain unchanged. Display account parameters are not accepted in rule-write payloads.

## Matching and storage

`apply_categories._load_rules` delegates to `services/category_rules.py`; both validated ingestion and the legacy pipeline therefore honor disabled entries. Legacy CSVs without `enabled`/`revision` remain enabled and last-duplicate-wins. A disabled last duplicate suppresses earlier duplicates, rather than reviving them. Keys use the existing import normalizer plus exact uppercase equality. Channels, amount, direction and account are not new conditions.

Only writes add optional `enabled`/`revision` columns. Unknown CSV columns and shadowed duplicate rows are retained. No reads migrate or create storage. No ledger migration is added.

The configured CSV parent owns:

- `category_rules.csv`: authoritative import rules, replaced atomically after staging/flushing a complete file.
- `.category_rules.csv.history/<event-id>.json`: local recovery/history events with exact before/after CSV copies and checksums, target key, row revisions, UTC time and optional undo reference. These are unencrypted local files and can contain private merchant rules. They are not exposed in browser API responses.
- `.category_rules.csv.lock`: exclusive cooperating-writer lock containing process ID. It is removed on normal completion/failure. A process crash can leave it deliberately blocking future writes.

Each v2 event has a unique event ID and explicit parent event ID; a CSV digest identifies bytes, not a historical edit (undoing creation can restore identical bytes). `.category_rules.csv.history/state` records the committed head/digest and at most one pending event. Under the existing writer lock, a first-write baseline state is staged before event evidence, then the pending state is published before replacing the CSV; successful saves finalize the new head. If interrupted, read-only inspection compares the pending event's distinct before/after digests with the CSV to distinguish prepared from applied without discarding event identity. Initial-state, journal, pending-state, CSV and final-state failures remain retryable or explicitly unknown after publication; no read repairs or migrates files. Full parent chains, checksums and target rows are validated, including orphan events and cycles. Unambiguous legacy digest-only history is readable and acquires v2 state only on a later write; ambiguous/damaged legacy history requires reconciliation. Atomic replacement is not a promise of power-loss durability across every filesystem.

Undo changes only the chosen key and requires its latest unchanged revision. Unrelated-key edits survive; later changes to that key, including ABA changes back to the same destination, reject old undo requests. Preview freezes both CSV digest and applied history head, so a create/remove round trip also invalidates outstanding previews despite identical CSV bytes. Preview also freezes definitions and exact historical evidence; a changed matching set or saved-category evidence requires another preview. Session ownership, expiry, literal approval, consumed write tokens, Host/Origin and CSRF guards remain enforced.

Disable retains an existing rule's exact saved category/subcategory pair even when that pair is obsolete in definitions; it cannot create a rule or combine a destination change with enabled-to-disabled transition. New rules, destination edits (including already-disabled rules) and re-enabling still require current definitions. Inside Edit rule, choose **Category / subcategory** or **Enabled / disabled** as separate changes. Category edits preserve the saved enabled state, including disabled rules. Status-only changes retain the exact saved pair, ignoring unsaved category fields. An obsolete pair can be disabled but cannot be re-enabled: first save a valid category while disabled, then explicitly enable it in a separate confirmation. Add rule starts enabled. The confirmation identifies current and proposed category/state and the all-account, future-import-only effect. **Undo this change** prepares the same explicit confirmation, which explains the restored state or removal of a newly added rule. Existing unknown-outcome/reload locks and history safety remain unchanged.

## Failure/recovery boundaries

SQLite transaction corrections and CSV rule changes are **not atomic together**. They are deliberately separate approvals. Rule-only changes do not refresh reports or write historical ledger rows.

If confirmation fails after publication, the response says the rule outcome is unknown and requires reload; it does not claim rollback. Failed confirmations cannot be replayed. Rule-only history inspection resolves the published event from versioned publication state and its matching CSV bytes after restart. A completed save is finalized to an explicit head; an interrupted pending publication can still be resolved without writes. As with the previous before/after recovery boundary, an external manual revert during an unfinished publication cannot be distinguished from a failed replacement by bytes alone: coordinate writers and reconcile rather than editing recovery files.

A stale lock or external manual CSV edit requires local operator reconciliation, not automatic overwriting. First stop/coordinate with every writer and retain the CSV plus the entire history directory. Check the lock's process ID before removing a genuinely abandoned lock. Inspect current digest and recovery before/after copies; never restore a complete old CSV as a substitute for targeted undo over later edits. There is intentionally no arbitrary-path restore endpoint or automatic recovery-on-read.

Safety snapshots now include optional `.category_rules.csv.history/<32-hex-event-id>.json` and v2 publication `state` members in their checksummed inventory. Verification and isolated restore retain the exact history needed for inspection and guarded undo. Older snapshots without history remain valid; they restore rules without inventing unavailable history. Snapshot creation takes the cooperating rule-writer lock, validates recovery events, copies CSV/history together and compares the source inventory/checksums before and after copying; concurrent external changes cause an explicit failure rather than publication of mixed state. Locks and atomic-write staging files are excluded. Existing exact inventory, checksum, SQLite integrity and link/reparse/path restrictions remain enforced. These unencrypted local snapshots are not encrypted/off-device disaster recovery.

Private generated rule history, the sibling lock, and CSV staging names are narrowly ignored by Git; authoritative `config/category_rules.csv` and `config/categories.json` remain stageable. Do not force-add recovery copies: they contain complete merchant-rule CSV versions.

## Verification

From the checkout root, use the installed application environment and Node.js on PATH:

```bash
.venv/Scripts/python.exe -m unittest tests.test_rule_maintenance tests.test_rule_maintenance_api tests.test_rule_corrections tests.test_rule_backup tests.test_rule_privacy tests.test_rules_display -v
.venv/Scripts/python.exe -m unittest discover -s tests -v
```

The suites use temporary synthetic ledgers and rule files, generated PDFs and executable JavaScript controller probes. They do not require real statements or the batch statement harness. Set `TMPDIR` to an existing writable temporary directory when needed; preserve the caller's setting. If `BANKSTATEMENT_PROJECT_ROOT` is set, it must point to the checkout under test, not a separate live installation. Optional MCP protocol checks require the isolated environment described in `agent-analysis.md`.

HTTP handlers live in `scripts/rule_routes.py` and are registered by the dashboard. Single exception corrections use audited `resolve_one`; bulk corrections retain their separate explicit selection and approval. Transaction identifiers in JSON responses remain lossless decimal strings.
